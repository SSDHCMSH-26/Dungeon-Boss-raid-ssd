# VISION_ROADMAP — 장기 목표와 로드맵 (2026-10-11 작성)

## 1. 목표 (사용자가 말한 그대로 정리)
**턴제 전략 RPG 스토리 게임**을 만든다. 한 개의 게임 계정으로 아이템·성장·스킬 해금·유닛 수집을 하며, 두 개의 스토리라인을 모두 깰 수 있다.

1. **용사 진영 스토리라인**: 유닛을 모으고 키우며 스토리 씬과 함께 여러 스테이지를 돌파, 보스 맵을 격파.
2. **보스 진영 스토리라인(디펜스 형식)**: 개인 스토리와 자기만의 맵(던전)을 꾸리고, 들어오는 용사 진영을 이겨 성장·스킬·아이템을 해금, 스테이지를 깨며 보스로서 새 맵을 얻는다.
3. **실전 멀티 1대1**: 자기가 해금한 보스·용사 진영으로 1대1 대전, 점수/랭킹 경쟁. **공평한 실력 승부**가 되어야 함.

사용자 상황: 개발 지식 없음(바이브코딩) → 한 단계씩 쉽게 설명 필요. 런칭·배포·법률은 세세히 안내 필요.

## 2. 가능한가? — 결론
- **기술적으로 가능**하다. 지금 만든 전투 시스템(규칙·AI·테스트 도구)이 이미 핵심 재료다.
- 다만 "한 판짜리 전투 프로토타입"에서 "계정·저장·스토리·성장·멀티가 있는 상용 게임"으로 가는 것이라 **규모가 몇 배~수십 배**로 커진다.
- 병목은 코드 작성 자체보다 ①**콘텐츠**(스테이지·스토리·맵·밸런스) ②**아트·사운드** ③**서버 운영** ④**법·행정** ⑤**테스트·밸런스 검증**이다. 코드는 AI가 대량 생산할 수 있지만 위 항목은 사용자의 결정·확인·시간이 계속 필요하다.
- 한 번에 다 만들려 하면 거의 반드시 실패한다 → **"수직 슬라이스(작은 완성판)" 먼저** 만들고 확장.

## 4. "공평한 멀티"를 위한 설계 원칙 (미리 정해야 함)
성장 요소 때문에 고레벨이 이기는 구조가 되면 공평하지 않다. 후보:
- **(A) 랭크전은 정규화**: 랭크전에서는 성장 수치를 무시하고 모든 유닛이 같은 기본 스탯. 해금은 "선택지의 폭"(쓸 수 있는 유닛·스킬 종류)만 넓힘.
- **(B) 포인트 예산 드래프트**: 해금한 것 중에서 정해진 포인트 안에서만 팀을 구성.
- **(C) 시즌 고정 로스터/밴픽**: 시즌마다 사용 가능한 구성을 제한하고 밴/픽.
- 원칙: 해금 스킬은 **상위 호환이 아니라 "옆그레이드"**(상황별 선택)로 설계.
- 추천: (A)+(C). 캠페인은 성장 반영, 랭크전은 정규화.

## 5. 구조 전환 필요 (현재 단일 HTML의 한계)
지금: 한 파일 안에 규칙·화면·AI가 얽힘 + 이미지 1.4MB. 계정·서버·콘텐츠 확장에는 부적합.
목표 구조:
- **규칙 코어**(화면 없는 순수 로직) — 서버와 클라이언트가 공용.
- **데이터 주도 콘텐츠**: 유닛·스킬·아이템·스테이지·대사를 JSON 으로 분리 → 콘텐츠를 늘릴 때 코드를 거의 안 건드림(토큰 절약의 핵심).
- **서버**(Node.js): 계정, 저장, 멀티 판정, 랭킹.
- **클라이언트**: 웹/스팀 공통 화면(이미지는 별도 파일).
- **자동 테스트**: 컴퓨터끼리 대전 시뮬 + 규칙 테스트(이미 도구 있음) → 기능 추가 때 기존 동작이 깨지지 않는지 확인.

## 6. 단계별 로드맵 + 작업량 추정 (매우 거친 추정)
※ AI 작업 토큰 기준. 오차가 크며 범위(스테이지 수 등)에 따라 몇 배 달라짐. A 단계가 끝난 뒤 실제 사용량으로 보정할 것.

| 단계 | 내용 | 추정 토큰 | 비고 |
|---|---|---|---|
| A. 기반 정비 | 개발 환경 전환(저장소), 규칙 코어 분리, 데이터화, 이미지 분리, 테스트 정비 | 100만~250만 | 모든 이후 작업의 효율을 좌우 |
| B. 서버·계정·저장 | 로그인, DB, 진행도 저장 | 50만~150만 | 외부 서버 배포는 사용자 작업 |
| C. 용사 캠페인 MVP | 스토리 씬 엔진, 스테이지 3개, 성장/해금 기본 | 200만~500만 | 시나리오·맵은 사용자 결정 필요 |
| D. 보스 디펜스 MVP | 맵 꾸미기 에디터, 침입자 웨이브, 보상/해금 | 250만~600만 | UI 작업량이 큼 |
| E. 랭크 멀티 | 서버 대전, Elo, 매칭, 정규화 규칙 | 150만~400만 | 정보 은닉·치트 방어 포함 |
| F. 출시 준비 | 스팀 패키징, 스토어 페이지, 법 문서, 최적화 | 100만~250만 | 법·행정은 사용자 작업 병행 |
| **합계(MVP)** | A~F | **약 850만~2,150만** | 콘텐츠 확장 제외 |
| G. 콘텐츠 확장 | 스테이지·유닛·스토리 추가 | 항목당 10만~40만 | 데이터화가 되어 있으면 하한에 가까움 |

- 시간 감각: 주 10~20시간을 쓸 때 MVP까지 **대략 6~12개월**(불확실). 아트·사운드·시나리오·테스트가 AI 작업보다 오래 걸릴 수 있음.
- **Pro 플랜 사용량이 이 총량을 감당할지는 알 수 없음**(한도가 토큰 수로 공개되지 않음). A 단계 후 실제 소모를 보고 플랜 변경/추가 크레딧을 판단.

## 7. 효율을 높이는 방법
1. **저장소 + 로컬 개발 환경으로 전환**: 큰 프로젝트는 채팅 아티팩트보다 컴퓨터의 코드 저장소에서 작업하는 편이 훨씬 효율적(필요한 파일만 읽고 테스트를 직접 실행). 설치·사용법은 단계마다 제가 쉽게 안내.
2. **데이터 주도 + 규칙 코어 분리**(위 5장) — 콘텐츠 추가 비용을 낮춤.
3. **결정 사항은 즉시 `GAME_SPEC.md` 에 기록**, 단계가 끝날 때마다 CHANGELOG/CODE_MAP 갱신(새 대화 시작 비용 절감).
4. **큰 요청은 작은 마일스톤으로 쪼개고 완료 기준을 먼저 합의**.
5. **자동 테스트**로 회귀를 막아 "고치다 다른 곳이 깨지는" 낭비 방지.
6. **이미지 별도 파일화**, 아트 스타일 가이드 고정(일관성).
7. 콘텐츠 제작은 템플릿화(스테이지 템플릿, 스토리 씬 템플릿).
8. 먼저 **작은 테스트 사용자**(지인)에게 보여 주고 방향 확인 → 큰 비용을 쓰기 전에 재미 검증.

## 8. 사용자가 맡아야 할 일 / 결정할 일

- 계정·서버·결제 정보 등록(제가 대신 못 하는 부분), 사업자등록·스팀웍스 가입

- 예산: 서버비, 스팀 보증금($100), 등급분류 수수료, 세무/법률 상담, (선택)외주 아트
