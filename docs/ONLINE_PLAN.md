# ONLINE_PLAN — 온라인 대전 · 랭킹 · 스팀 출시 계획

## 목표와 원칙
- 공정한 온라인 대전과 랭킹 → **서버가 규칙을 판정**(서버 권위 구조). 클라이언트는 입력·표시만.
- 이 게임은 턴제라 서버 부하와 비용이 매우 낮음 (월 수천~수만 원대 서버로 시작 가능).
- 웹에서든 스팀에서든 플레이어는 자기 기기의 코드 사본을 고칠 수 있음 → 서버 검증이 없으면 치트 가능.

## 현재 구조의 문제점 (공개 서비스 전 반드시 해결)
1. 온라인 모드가 **상태 전체를 양쪽에 동기화** → 함정·폭탄·구덩이·함정 상자 위치가 개발자 도구로 보임.
2. 클라이언트가 직접 HP·점수를 계산 → 조작 가능.
3. 동기화가 Claude 아티팩트 전용 저장소(`db`)라 **Claude 밖에서는 동작하지 않음**(웹/스팀 배포 시 온라인 대전 불가).
4. 랭킹/계정/매칭/재접속/제한시간 처리 없음.

## 목표 구조
```
[클라이언트(웹/스팀)] --입력(스킬, 칸)--> [게임 서버(Node.js, WebSocket)]
                     <--진영별로 필터링한 상태--
                              |
                         [DB: 계정, 매치 기록(행동 로그), Elo]
```
- 규칙 코드(상태·행동·정산)를 **화면 코드와 분리한 순수 모듈**로 만들어 서버와 클라이언트(혼자하기)가 같이 사용.
- 서버가 하는 일: 입력 합법성 검사(내 차례, AP, 쿨타임, 사거리, 위치) → 규칙 적용 → 진영별 시야에 맞게 필터링한 상태 전송(상대 함정은 안 보냄, 공개된 것만).
- 행동 로그 전체를 저장 → 리플레이, 이상 판 검증, 분쟁 해결.
- Elo/Glicko 점수는 서버만 계산. 탈주 패널티, 턴 제한시간, 재접속, 같은 점수대 매칭 큐.
- 로그인: 웹=소셜 로그인, 스팀=스팀 인증 티켓 검증. 스팀 리더보드/업적은 Steamworks.

## 단계별 계획과 추정 (AI 작업량 · 매우 대략적)
| 단계 | 내용 | 추정 토큰 | 추정 시간 |
|---|---|---|---|
| 1 | 규칙 로직을 화면 코드에서 분리(순수 모듈화). 혼자하기는 계속 동작해야 함 | 30만~80만 | 2~4시간 |
| 2 | 로컬 Node 서버 프로토타입: 두 클라이언트가 서버를 통해 대전 | 20만~50만 | 1~3시간 |
| 3 | 정보 은닉, 계정, Elo 랭킹, 행동 로그 저장 | 20만~50만 | 1~3시간 |
| 4 | 테스트·안정화(끊김, 제한시간, 치트 시도 방어) | 20만~60만 | 2~5시간 |
| 합계 | | 약 100만~250만 | 약 6~15시간 (여러 세션에 분할) |
※ 외부 서버 배포·스팀 계정/Steamworks 연동은 AI 환경에서 직접 못 하므로 **안내만** 가능(사용자가 직접 수행).
※ Pro 플랜 사용량 한도는 토큰 수로 공개되지 않음(5시간 세션 + 주간 한도). 한 번에 못 끝내므로 단계별로 나눠서 진행하고, 단계가 끝날 때마다 이 폴더의 문서를 갱신해 둘 것.

## 권장 순서와 이유
- **규칙이 어느 정도 굳은 뒤** 1단계를 한 번에 몰아서 진행(분리 후에는 규칙 수정 때 양쪽을 고쳐야 하므로).
- 1단계 시작 전 `GAME_SPEC.md`, `CODE_MAP.md` 를 먼저 최신화.
- 이미지(base64)를 별도 파일로 분리하면 이후 모든 수정 작업의 토큰이 줄어듦(코드 150KB / 이미지 1.4MB).

## 엔진 선택지
- **JS 유지 + Node 서버(권장)**: 지금 코드를 재사용. 스팀은 Electron/Tauri 로 패키징 + Steamworks 바인딩.
- Godot/Unity 로 이전: 스팀 연동·그래픽은 좋지만 규칙 전부 재작성. 규칙이 계속 바뀌는 동안은 비추천.
- 서버리스(Firebase 함수 등): 서버 관리는 줄지만 이 정도 복잡한 규칙을 쪼개기엔 번거로움.
